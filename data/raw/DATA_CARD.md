# Data card - SYNTHETIC demo data (not real)

This is the card of the project's built-in demo dataset. A second simulated dataset with a different schema is described in
`examples/retail_style_fixture/README.md`. Real datasets are described by their own config in `configs/`.

| | |
|---|---|
| **Source** | Generated by `src/generate_data.py` (seed 42). **Not real customer data.** |
| **Licence / usage** | No external licence: the data is produced by the code in this repository. |
| **Period** | 2024-01-01 to 2025-12-31 (customers register throughout the period) |
| **Size** | 6,000 customers, ~148k raw transaction lines (60,575 purchase orders after cleaning) |
| **Why simulated** | Lets the whole project be reproduced without privacy or licensing constraints, and lets realistic data-quality problems be injected deliberately. |

## Files
`customers_raw.csv` - `customer_id, customer_age, customer_gender, customer_location, customer_registration_date`
`transactions_raw.csv` - `transaction_id, order_id, customer_id, product_id, product_category, quantity, unit_price, discount, payment_method, transaction_date`
(one row per order line; returns have ids prefixed `R` and negative quantity; discount is a fraction in [0, 1]; amounts are in an unspecified currency)

## How customers are simulated
Each customer has a hidden type (loyal, regular, occasional, bargain, fading) that sets order rate, basket size, discount sensitivity and a daily probability of **permanently leaving**. Orders follow a seasonal Poisson process; activity fades over the ~60 days before a customer leaves. Customers choose a favourite category ~50% of the time.

## Injected data-quality problems (found and handled by `src/data_processing.py`)
mixed date formats, case/whitespace variants of categories, payment methods, genders and cities, exact duplicate rows, non-return negative or zero quantities, zero or negative prices, discounts stored as percentages, impossible and missing ages, legitimate returns.

## Limitations
* The churn mechanism is known to the simulator, so model results demonstrate the **method**; they say nothing about any real business.
* No marketing activity, price changes, stock-outs, channels or competitors are simulated.
* Churn hazards are constant per type; real churn has richer causes.
* To use real data, write a YAML adapter config (`configs/template.yaml`): the pipeline never depends on these column names.
